# 메일 SPA (`mail.mgnt.kr`) — 구조와 함정

2026-09-15 작업. 기존 메일 화면(`/mail`)은 **그대로 두고** 새 화면을 나란히 올렸다.
같은 날 새 화면을 `work.mgnt.kr/webmail/` 에서 **`mail.mgnt.kr` 전용 호스트로 옮겼다**(§0).

---

## 0. 주소가 옮겨졌다 — mail.mgnt.kr

| | 지금 |
|---|---|
| 정식 주소 | **`https://mail.mgnt.kr/`** — 루트가 곧 메일 화면 |
| 옛 주소 | `work.mgnt.kr/webmail/` → **301** 로 넘김 |

- `mail.mgnt.kr` 은 **원래 있던 이름이다** — `mgnt.kr` 의 MX(메일 서버)다.
  건드린 건 443 뿐이고 **25/587/993 스트림과는 겹치지 않는다.**
  443 은 예전에 시놀로지 webmail 로 가다 인증서 만료로 끊긴 자리다(VPS `stream` 맵 주석).
- 백엔드는 **work 와 같은 ERP(8501)** 한 벌이다. 앱이 `Host` 를 보고 갈린다
  (`app.py` 의 `_is_mail_host()` / `MAIL_APP_HOST`). 새 서비스·새 포트는 없다.
- **번들 base 는 여전히 `/webmail/`** 이다. `mail.mgnt.kr/` 이 내주는 index.html 이
  `/webmail/assets/*` 를 부른다 → `serve_mail_app()` 은 **호스트를 가리지 않고 파일을 내주고,
  화면 진입(index.html)만** mail 호스트로 모은다. 옛 탭이 자산을 계속 받을 수 있는 이유다.
- **세션 쿠키는 호스트별이다.** 그래서 로그인을 **건네받는다**(`/api/app/handoff`):

  ```
  mail.mgnt.kr/ 부팅 → session-token 401
    → https://work.mgnt.kr/api/app/handoff?to=https://mail.mgnt.kr/
        (work 에 세션 있으면 60초짜리 코드 발급 / 없으면 ERP 로그인부터 → 되돌아옴)
    → https://mail.mgnt.kr/api/app/handoff-land?code=…&next=/
    → mail 호스트에 세션 생성 → /
  ```

  `SESSION_COOKIE_DOMAIN = '.mgnt.kr'` 한 줄이면 끝나지만 **쓰지 않았다** —
  그러면 ERP 세션 쿠키가 team(mattermost)·cloud·docs·db 등 남의 서비스에까지
  매 요청 실려 가고, 플라스크 쿠키는 서명만 돼 있어 **권한 목록까지 읽힌다.**

  - `to` 는 **허용 호스트 목록**으로 묶는다(`_handoff_hosts()`). 없으면 남의 주소로
    코드를 흘리는 열린 리다이렉트가 된다.
  - 코드는 상태 없는 HMAC 이고 **수명 60초**다. 일회성은 아니다.
  - SPA 는 **한 번만** 건네받으려 한다(`sessionStorage` 의 `erp_handoff_tried`).
    받고도 세션이 안 잡히면 그대로 무한히 돈다.
  - **`goLogin()` 은 한 페이지에서 한 번만 나간다.** 401 은 겹쳐서 떨어지는데,
    뒤엣것이 앞의 이동을 취소해 이어받기가 실제로 끊겼다(`net::ERR_ABORTED`).
  - 로그아웃은 아직 호스트별이다 — **ERP 에서 로그아웃해도 메일 세션은 남는다**(최대 8시간).
- 로그인 복귀 주소는 **지금 서 있는 경로**를 쓴다(`window.location.pathname`).
  호스트마다 엔트리가 `/` 와 `/webmail/` 로 달라서다. 새 버전 감지(`isStaleBuild`)도 같다.
- 301 은 **브라우저가 영구 캐시한다.** 되돌리려면 사용자 캐시가 걸림돌이다
  (`app.py` 의 `code=301` 한 자리).
- **호스트를 건너가는 링크는 주소를 박는다** (`src/lib/erp.js`) — 왼쪽 위 로고는
  `MAIL_ORIGIN`(메일 첫 화면), 그 옆 `ERP ↗` 는 `erpUrl()`.
  상대경로로 두면 "ERP로 돌아가기" 가 메일을 다시 여는 꼴이 된다 — 여기선 `/` 가 메일이다.
  반대로 **메일 본문에 실려 나가는 대용량 첨부 링크는 여기와 무관하다** —
  그쪽은 `.env` 의 `FLASK_DOMAIN`(= work.mgnt.kr)을 본다(`routes/mail.py`).

nginx 는 두 군데를 같이 손댔다.

| 어디 | 무엇 |
|---|---|
| VPS `/etc/nginx/nginx.conf` | `listen 4443 ssl; server_name mail.mgnt.kr;` → `100.110.60.7:8501` (work 와 같은 대용량 설정) |
| webserver `sites-available/lan-direct.conf` | work 블록 `server_name` 에 `mail.mgnt.kr` 추가 (사내 DNS 가 가리키면 tailnet 을 건너뛴다) |

## 1. 화면이 둘이다

| | 경로 | 코드 | 상태 |
|---|---|---|---|
| 기존 | `/mail`, `/mail/personal`, `/mail/compose` … | `templates/mail_*.html` + `static/js/mail.js` | 유지 (익숙한 사용자용) |
| 신규 | **`mail.mgnt.kr/`** (자산은 `/webmail/`) | `mail_app/` (Vite + React + zustand) | 3-pane 목록·읽기창, 작성 페이지 |

**둘은 같은 `/mail/api/*` 를 공유한다.** 백엔드는 한 벌이므로 API 수정은 양쪽에 같이 먹지만,
화면 동작은 완전히 다르다. **버그 제보가 오면 어느 화면인지부터 확인한다.**

- 빌드: `cd mail_app && npm run build` → `mail_app/dist/` (git 제외, 서버에서 빌드)
- 서빙: `app.py` 의 `serve_mail_app()` + `index()` 의 호스트 분기 — `/m/` 모바일 SPA 와 같은 방식.
  메일 호스트는 **모바일 판별보다 먼저** 본다 — 메일 주소로 들어온 사람에게 `/m/` 은 엉뚱하다.
- 인증: **Bearer 토큰**. 부팅 때 `/api/app/session-token` 으로 PC 세션을 한 번 교환한다.
  세션 쿠키를 안 쓰니 CSRF 토큰이 필요 없다.

### SPA 는 새로고침 전까지 옛 코드를 돈다

재배포해도 열어둔 탭은 그대로다. 겉보기엔 멀쩡한데 **새 기능만 조용히 안 먹는다.**
실제로 대용량 첨부 링크가 이 때문에 빠져서 한참 헤맸다. 번들 파일명이 바뀌면 상단에 띠를
띄우는 `StaleBanner` 를 넣어뒀다. **"안 된다"는 제보가 오면 새로고침부터 시켜본다.**

### 메일함 구성

- **받은편지함 / 내게쓴메일함은 같은 INBOX 를 주소로 나눈다** (`NOT FROM "내주소"` / `FROM "내주소"`)
- 안읽음 뱃지도 같은 조건으로 따로 센다. **`/mail/api/folders` 의 숫자는 쓰지 않는다** —
  워커별 메모리 캐시라 8워커가 서로 다른 값을 준다
- 예약 발송함은 IMAP 폴더가 아니라 `light_sync.mail_scheduled` 를 보여주는 화면이다
- 본문 편집기는 라이브러리 없이 `contenteditable` + `execCommand`.
  의존성은 `react`·`react-dom`·`zustand` 셋뿐 — **UI 라이브러리를 새로 넣지 않는다**

## 1-2. 검색 — 기본 · 상세

| | 무엇 | 어디 |
|---|---|---|
| 기본 | 한 낱말을 제목·보낸사람·본문 여러 자리에서 훑는다(OR) | `/mail/api/search` |
| 상세 | 조건을 **모두** 만족하는 것만 남긴다(AND) | `/mail/api/search-advanced` |

상세검색 조건: 보낸사람·받는사람·제목·본문·기간·첨부있음·안읽음·중요.

- **IMAP 검색식은 문자열로 이어붙이지 않는다.** `client.search_advanced()` 에 imapclient
  규격의 **리스트**를 넘긴다 — 따옴표와 한글(UTF-8)은 imapclient 가 처리한다.
  `f'FROM "{addr}"'` 로 만들면 값에 따옴표가 섞이는 순간 검색이 통째로 깨진다.
- `BEFORE` 는 그 날을 포함하지 않는다 — 종료일까지 담으려면 **하루 뒤로 민다.**
- IMAP 에 "첨부 있음" 조건은 없다. 목록이 첨부 아이콘을 띄울 때 보는 것과 같은 잣대
  (`HEADER Content-Type multipart/mixed`)를 쓴다 — 그래야 결과와 아이콘이 어긋나지 않는다.
- **받은편지함/내게쓴메일함은 같은 INBOX 다.** 검색도 그 칸 안에서만 찾아야 하므로
  화면이 `self=exclude|only` 를 보내고 서버가 계정 주소로 `NOT FROM` 을 덧붙인다.
  (기본 검색은 이 구분을 아직 안 한다 — 내게쓴메일이 섞여 나온다)
- 결과는 **최신순 200건까지**. 잘리면 `truncated` 로 알려주고 화면이 그렇게 적는다.
- uid 만 주지 않고 **메시지까지 채워서** 준다 — 목록이 그대로 그릴 수 있어야 한다.
- 조건이 하나도 없으면 400 이다. `ALL` 로 넘어가면 그냥 목록이지 검색이 아니다.

### 툴바 배치

검색·상세·새로고침은 **목록 칸 위**에 둔다(`.list-tools`). 예전엔 `margin-left: auto` 로
읽기창 쪽 끝에 밀려 있어서 **무엇에 대한 검색인지 읽히지 않았다.**
목록 밀도(크게 52 / 보통 42 / 좁게 34px)만 오른쪽 끝이다 — 목록을 다루는 게 아니라 보기 설정이다.

상세검색이 걸리면 **무엇으로 걸렀는지 조건 딱지를 결과 위에 남긴다.** 안 남기면
"왜 이것만 나오는지" 를 화면 어디에서도 읽을 수 없다.

## 1-3. 메일쓰기 — 임시저장 상태

보내기·예약·임시저장과 **같은 줄 맨 오른쪽**에 **저장했는가 · 몇 번째인가 · 언제인가**
를 띄운다(`DraftStatus.jsx`).

| 표시 | 뜻 |
|---|---|
| 임시저장 안 됨 | 아직 한 번도 안 눌렀다 |
| 저장 중… | 보내는 중 |
| **저장됨** + `v2 · 16:59:10 · 자동` | 2번째 임시저장(자동), 그 뒤로 손대지 않았다 |
| **저장 후 변경됨** + `v2 · 16:59:10 · 자동` | 저장한 뒤 내용을 고쳤다(5초 뒤 자동저장이 돈다) |

- **자동저장이 있다** — 5초 조용하면 한 번 저장한다(`_scheduleAutosave` → `_autosave`).
  손저장과 **같은 길**(`saveDraft`)을 쓰므로 임시보관함에 남는 건 늘 한 통이다.
  마지막 저장이 자동이면 `· 자동` 이 붙는다.
- **자동저장이 쉬는 경우는 화면에 적는다.** 조용히 저장 안 되는 게 제일 나쁘다:
  예약본 수정 / 아직 아무것도 안 씀 / 고친 게 없음 / 저장·발송 중 /
  **첨부가 2MB 초과** — 첨부는 저장할 때마다 다시 올라간다. 40MB 를 5초마다
  올릴 수는 없다. 이때만 문구를 띄운다(`첨부가 커서 자동저장 안 함`). 손저장은 된다.
- 고쳤는지는 **내용 지문**(`draftSignature()`)으로 가린다. 저장한 순간의 지문을 들고
  있다가 지금 것과 다르면 '변경됨'이다. 첨부는 파일 자체가 아니라 이름·크기만 본다.
- **지문은 요청을 보내기 직전의 내용으로 뜬다.** 응답이 온 시점에 뜨면 저장이 오가는
  동안 고친 것을 "저장됨"으로 삼켜버린다.
- `v` 는 저장 **횟수**다. 서버에는 임시본이 한 통만 남는다(`replace_uid` 로 갈아끼운다).
- 예약 메일 수정(`editScheduled`)에는 안 띄운다 — 거긴 임시저장이 아니라 예약본 고치기다.

`canLeave()` 도 같은 지문을 본다 — **저장해 둔 그대로면 "사라집니다" 를 묻지 않는다.**
임시보관함에 남아 있는데 사라진다고 하면 거짓말이다. 손댔는지 판정(`isTouched`)은
경고와 자동저장이 **같은 잣대**를 쓴다. 한쪽만 손댔다고 보면 빈 껍데기가 쌓이거나
쓴 게 소리 없이 날아간다.

## 1-4. 주소록 — 세 칸으로 갈라 둔다

| 칸 | 무엇 | DB |
|---|---|---|
| **내 주소록** | 나만 본다. 메일을 보내면 받는사람이 여기 저절로 쌓인다 | `user_id = 나`, `is_shared=false` |
| **회사 공용** | 전 직원이 보고 고친다. **옛 주소록에서 가져다 둔 930건이 여기 있다** | `user_id IS NULL AND is_shared` |
| **사내 직원** | `users` 로 만들어 내는 자리 — 저장하지 않는다. 사람이 들고 나면 따라온다 | (없음) |

- 화면: `mail_app/src/components/ContactsPage.jsx`, 스토어 `store/contacts.js`,
  옛 화면은 `/mail/settings` 의 주소록 탭(같은 API 를 쓴다).
- **들어가는 문은 사이드바 「주소록」 하나다.** 세 칸을 가르는 일은 들어가서 탭으로 한다 —
  왼쪽에 세 줄을 늘어놓으면 메일함과 섞여 읽힌다.
- 메일쓰기 툴바의 [주소록] 은 고르기 창이다(`ContactPicker.jsx`). 고른 뒤에
  **받는사람·참조·숨은참조 중 어디에 넣을지 그때 고른다** — 칸을 먼저 고르게 하면
  참조에 넣으려다 받는사람에 들어가는 실수가 잦다.
- **남의 개인 주소록은 어떤 경로로도 안 새어 나간다.** 조회·저장·삭제·내보내기가
  모두 `_book_filter()` 한 곳에서 `user_id` 로 먼저 자른다. 자동완성(`/contacts/suggest`)도
  같은 잣대를 쓴다 — 예전의 `or_(is_shared, user_id==나)` 는 남이 공유로 표시한
  개인 줄까지 끌어왔다.
- 저장은 **같은 칸에 같은 주소가 있으면 새 줄을 만들지 않고 그 줄을 고친다**(대소문자 무시).
  "저장했는데 두 줄이 됐다" 가 주소록에서 제일 흔한 불만이다.
- `phone` 칸이 생겼다(2026-09-15). 예전엔 vCard 의 TEL 을 메모에 섞어 넣었다.

### 가져오기 / 내보내기

- 파서는 **`modules/services/vcard.py` 한 벌**이다. 화면의 [가져오기]와
  `scripts/import_synology_contacts.py` 가 같은 것을 쓴다.
- 실제로 걸렸던 것들: 줄 접힘(공백 들여쓰기) · **아웃룩 2.1 의 QUOTED-PRINTABLE 한글**
  (줄 끝 `=` 는 다음 줄로 이어짐, 이어지는 줄은 들여쓰기가 없다) · `EMAIL;TYPE=* Other:` ·
  구글의 `item1.EMAIL` 접두사 · **다음(Daum)은 그룹 이름을 `ORG:_1` 로 흘려보낸다**
  (회사란에 `_1` 이 들어가므로 `^_\d+$` 는 버린다).
- 고르면 **저장하지 않고 먼저 센다**(`dry_run=1`). 수백 건이 말없이 쏟아진 뒤에
  되돌리는 것보다 낫다. 이미 있는 주소는:
  - 기존 이름이 메일 앞부분 그대로면(자동수집 흔적) 제대로 된 이름으로 바꾼다
  - 회사·전화·메모는 **비어 있을 때만** 채운다 — 사람이 적어 둔 것을 덮지 않는다
- 실측(2026-09-15): `daum contact.vcf` 268장을 회사 공용에 다시 넣어 보면
  **추가 0 · 갱신 1 · 이미있음 267** 이다. 기존 데이터가 그대로 살아 있다는 뜻이다.
- 공유 주소록에는 `uq_mail_contacts_shared_email` 부분 인덱스가 있다.
  **개인 주소록에는 일부러 안 걸었다** — 같은 주소를 다른 이름으로 들고 있는 줄이
  실제로 있다(`sw6042958@hanmail.net` = 업체이자 감독). 제약 하나 걸자고 사람이
  적어 둔 것을 지우지 않는다.

## 1-5. 보낸사람 이름은 버튼이다

목록·읽기창에서 보낸사람을 누르면 **메일 보내기 · 주소록에 추가 · 이 사람 메일 검색 ·
주소 복사** 가 뜬다(`SenderMenu.jsx`).

- 메뉴는 **`position: fixed`** 다. 목록 줄 안에 `absolute` 로 붙이면 스크롤 영역에 잘려
  절반이 안 보인다. 화면 끝에서는 되밀고, 아래가 모자라면 위로 편다.
- 목록에서는 **줄 클릭(메일 열기)과 겹치므로 전파를 끊는다**(`stopPropagation`).
- 목록이 스크롤되면 메뉴만 제자리에 남아 엉뚱한 줄을 가리킨다 — 그냥 닫는다.
- 주소 복사는 `navigator.clipboard` 가 막힌 경우(비 https 등) textarea 로 되돌린다.

## 1-6. 폴더마다 뜻이 다른 것들

| 무엇 | 규칙 | 왜 |
|---|---|---|
| **안읽음 표시** | 보낸편지함·임시보관함에는 **안 띄운다** (목록 점·사이드바 뱃지·안읽음 필터 셋 다) | 목록의 점은 IMAP `\Seen` 하나를 그대로 그린 것이다. 내가 보낸 사본에는 읽고말고가 없다. 우리가 보낼 때는 `\Seen` 을 붙이지만(`append_to_sent`) 휴대폰·아웃룩이 넣은 사본에는 없어서, **같은 목록에서 어떤 줄만 점이 찍혔다** |
| **다시 보내기** | 보낸편지함에서만 (`isSentFolder`) | 받은 메일에서 누르면 원본의 받는사람(=나)이 실려 나에게 다시 보내는 꼴이 된다 |
| **다시 보내기가 가져오는 것** | 제목·본문·첨부만. **받는사람·참조는 비운다** | 썼던 내용을 다시 쓰는 쓰임이라, 주소가 남아 있으면 지우는 걸 잊고 엉뚱한 사람에게 나간다 |

잣대는 `lib/folders.js` 한 곳에 둔다. 셋 중 하나만 남으면 "여긴 왜 다르냐" 가 된다.

## 1-7. 화면 상태 두 가지

- **메일을 쓰는 동안에는 사이드바에 활성 메일함이 없다.** 가운데는 작성 화면인데
  왼쪽만 받은편지함이 켜져 있으면 지금 무엇을 보고 있는지가 두 곳에서 다르게 읽힌다.
  눌러서 옮겨 간 메일함이 그때 켜진다.
- **나갈 때 묻지 않는다 — 임시보관함에 넣고 보낸다**(`canLeave` → `_stashDraft`).
  메일함을 누른 사람은 그 메일함을 보려는 것이지 예/아니오를 고르려는 게 아니다.
  확인창이 뜨면 한 번 눌러서는 안 옮겨진다. 넣었다는 것은 아래 띠(`notice`)로 알린다.
  **못 넣는 경우에만** 예전처럼 묻는다: 예약본 수정 · 저장/발송 중 ·
  대용량 첨부가 붙어 있을 때(나가면서 temp 를 지우므로 저장본이 깨진다) ·
  첨부가 2MB 를 넘을 때(저장할 때마다 다시 올라간다).
  작성창은 곧 비워지므로 **저장할 내용을 인자로 들고 간다** — `get().active` 를 보면
  이미 없다.
- **읽기창 최대화**(읽기창 오른쪽 위 버튼 / `Esc` 로 복귀) — **접는 것은 목록뿐이다.**
  왼쪽 메일함 칸도, 위 툴바(메일함 이름·검색)도 그대로 둔다. 경계는 **목록이 있던
  자리까지**다 — 읽기창이 화면 맨 위까지 올라오면 지금 어느 메일함을 보고 있는지가
  화면에서 사라지고, 사이드바까지 지우면 갈 곳이 없어져 화면이 멈춘 것처럼 보인다.
  **브라우저에 저장하지 않는다**: 켜 둔 채 새로고침하면 목록도 툴바도 없는 빈
  읽기창만 남아 "메일함이 사라졌다" 가 된다. 메일을 닫거나 메일함을 옮기면 저절로 풀린다.
  `Esc` 는 **전체화면부터 푼다** — 한 번에 메일까지 닫히면 넓게 보려다 읽던 것을 잃는다.

## 1-8. 뒤로가기 · 앞으로가기 (해시 라우팅)

`lib/route.js`. 예전엔 주소가 하나뿐이라 **뒤로가기를 누르면 메일 밖으로 나갔다.**

```
#/mail/INBOX        #/mail/INBOX/1234     #/selfbox   #/scheduled   #/contacts/personal
```

- **경로가 아니라 해시다.** `/INBOX` 같은 경로로 쌓으면 그 상태에서 새로고침했을 때
  서버가 ERP 라우트로 받아 404 다. SPA 가 `/`(mail 호스트)와 `/webmail/`(work 호스트)
  두 자리에서 열리는 것도 같은 이유로 경로를 못 늘린다.
- 기록은 **스토어 구독 한 곳**에서 쌓는다(`useMail`·`useContacts`·`useCompose`).
  화면을 옮기는 자리마다 심으면 반드시 어딘가를 빠뜨린다.
- **메일쓰기는 주소에 안 적는다.** 뒤로가기로 빈 작성창이 되살아나면 껍데기라 더 헷갈린다.
  작성 중 뒤로가기는 작성창을 닫고 간다 — 쓰던 게 있으면 늘 하던 대로 묻고,
  **취소하면 `history.forward()` 로 자리를 지킨다.** 이때 되돌아오는 popstate 한 번은
  흘려야 한다(`skipNextPop`) — 안 그러면 같은 것을 두 번 묻는다.
- 뒤로가기를 적용하는 동안에는 기록을 쌓지 않는다(`applying`). 안 그러면 뒤로가기가
  새 기록을 만들어 영영 못 빠져나온다.
- **거르개(검색·빠른필터·라벨)는 주소에 안 적는다.** 주소에 남는 것은 "지금 어느 메일함의
  어느 메일을 보고 있는가" 뿐이다. 셋 중 하나만 주소에 넣으면 어떤 건 뒤로가기로 풀리고
  어떤 건 안 풀려서 규칙이 더 안 읽힌다. 그래서 라벨로 거른 상태도 안 적는다
  (2026-09-16 에 라벨을 붙이며 다시 검토한 결과다 — 셋 다 넣든 셋 다 빼든이지,
  하나만 넣지는 않는다). 거르개를 푸는 문은 화면에 따로 있다: 툴바의 조건 딱지 ✕.

## 1-9. 다크모드 · 스크롤바

- 색은 `styles.css` 맨 위 `:root` 의 **토큰 목록**에만 있다. 규칙마다 색을 박아 두면
  테마가 둘이 되는 순간 반드시 어딘가 하나가 밝은 채로 남는다.
  2026-09-15 에 되풀이되던 하드코딩 색(행 hover·선택·경고띠·배지 등)을 전부
  뜻 있는 토큰으로 묶었다(`--row-hover`, `--panel-soft`, `--warn-bg` …).
- 고른 테마는 `<html data-theme="light|dark">` 로 박는다(`lib/theme.js`).
  **자동이면 아무것도 안 박고** `prefers-color-scheme` 이 OS 를 따라간다.
  그래서 dark 토큰 블록이 둘이다 — `:root[data-theme="dark"]` 와
  `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) }`.
  `:not([data-theme="light"])` 를 빼면 **OS 가 어두울 때 '밝게' 를 골라도 어두운 채로 남는다.**
- 테마는 **React 가 그리기 전에** 건다(`main.jsx`). 그린 다음에 걸면 흰 화면이 한 번 번쩍인다.
- 어두운 테마에서 파랑은 한 단 밝히고 **그 위 글씨는 어둡게** 둔다(`--on-accent`).
  밝은 파랑 버튼에 흰 글씨를 얹으면 대비가 3:1 도 안 나온다.
- **남이 보낸 HTML 메일은 흰 종이 위에 그대로 올린다**(`--mail-canvas`).
  본문 색만 뒤집으면 표·서명 이미지가 제 색과 어긋나 더 읽기 나빠진다.
- **떠 있는 판(메뉴·모달)에는 어두울 때만 테두리를 준다**(`--float-border`).
  검은 그림자는 검은 바탕에서 안 보인다 — 보낸사람 메뉴가 배경과 안 갈렸다.
- 스크롤바는 **모든 스크롤 영역**에 건다(`*::-webkit-scrollbar`, track 은 투명).
  예전엔 `.msg-list`·`.read-body`·`.sidebar` 만 손봤는데 **실제로 스크롤되는 건
  `.sidebar-scroll`** 이라 메일함 칸만 기본 스크롤바로 남아, 바탕색과 다른 띠가
  경계선처럼 보였다. track 을 투명으로 두면 어느 자리든 그 자리 바탕이 비친다.

## 1-10. 환경설정 창 (톱니바퀴)

툴바 오른쪽 끝, **밀도(크게·보통·좁게) 바로 옆**. 화면을 손보러 온 손이 거기까지 와 있다.
구성은 네이버·다음 메일의 환경설정을 따랐다 — 화면 / 보내기 / 부재중 자동응답 /
자동 전달 / 자동 분류 / 단축키·도움말.

| 칸 | 어디에 저장되나 | 무엇 |
|---|---|---|
| 화면 | **브라우저**(`webmail_prefs`·`webmail_theme`) | 테마, 목록 줄 높이, 한 쪽에 보여줄 메일 수(25/50/100), 목록 너비 되돌리기 |
| 보내기 | 서버 (`/mail/api/account`) | 보내는 사람 이름. 서명은 ERP 계정정보로 만들어져 **보기만** 한다 |
| 부재중 자동응답 | 서버 (`/mail/api/auto-reply`) | 사용·기간·제목·내용·한 사람당 한 번 |
| 자동 전달 | 서버 (`/mail/api/auto-forward`) | 주소 추가/삭제, 사용, 원본 보관 |
| 자동 분류 | 서버 (`/mail/api/rules`) | 규칙 **목록·삭제·지금 적용**. 새 규칙 만들기는 ERP 설정으로 보낸다 — 조건이 여러 줄이라 좁은 창에서 만들면 실수가 난다 |

- **누르면 저장인지, [저장]을 눌러야 하는지를 칸마다 글로 적는다.** 어디까지 저장됐는지
  모르는 설정창이 제일 나쁘다.
- 자동응답·전달·분류는 **계정마다 다르다.** 지금 어느 계정 설정을 보고 있는지 늘 위에 적는다.
- **한 쪽에 보여줄 메일 수는 `prefs.perPage` 다** — 예전엔 `loadMessages()` 안에 50 이 박혀 있었다.

### 여기서 고친 보안 구멍 (2026-09-15)

`auto-reply`·`auto-forward`·`rules` API 는 **`account_id` 를 그냥 믿고 있었다.**
메일을 열지 않으니 `_get_mail_client()` 를 부를 일이 없었고, 그래서 권한 확인도 없었다.
남의 계정 번호만 적으면 **자동전달 주소를 바꿔 남의 메일을 받아볼 수 있었다.**

`_account_allowed(db, account_id)` 를 만들어 세 묶음 전부에 걸었다(잣대는 `_get_mail_client`
와 같다 — 내 계정이거나 내가 권한을 받은 공용계정). 고치기·지우기는 **넘어온 account_id 가
아니라 그 줄이 달린 계정**을 본다. 실측: 내 계정 200, 남의 계정 403.

## 1-11. 메일함 관리 · 순서 · 그룹

- 만들기·이름 바꾸기·지우기는 **IMAP 폴더를 직접** 건드린다 — 아웃룩·휴대폰에도 그대로 보인다.
- **기본 메일함(받은편지함·보낸편지함·임시보관함·휴지통·스팸)은 못 고친다.** 이름이 바뀌는
  순간 우리 화면도, 발송 사본 저장(`append_to_sent`)도 그 폴더를 못 찾는다.
- 지울 때는 **하위 메일함까지 한 묶음**으로 본다. 부모만 지우면 IMAP 이 껍데기(`\NoSelect`)를
  남겨서, 화면에는 그대로 보이는데 열리지 않는다 — "지웠는데 안 지워졌다" 가 된다.
  하위를 먼저(깊은 것부터) 지우고 부모를 지운다. 이때 나는 `NONEXISTENT` 는 실패가 아니다.
- 비어 있지 않으면 **409 + 통수**를 돌려주고 화면이 다시 묻는다. IMAP DELETE 는 안에 든
  메일을 같이 지우고 휴지통으로 보내지도 않는다.
- 계층 구분자는 서버가 정한다(`/` 또는 `.`). `folder_delimiter()` 로 **읽어서** 쓴다 —
  박아 두면 다른 서버에서 `INBOX.업무` 가 통째로 한 이름이 된다.
- **기본 메일함 판정에는 한글 이름도 넣고, 띄어쓰기는 지우고 본다.**
  서버에 사람이 만든 `임시 보관함`(공백 포함)·`내게쓴편지함` 이 실제로 있었다.
  공백 하나로 판정이 새면 그 폴더만 고칠 수 있게 남아 화면이 어긋난다.
  잣대는 두 곳이 같은 이름을 쓴다 — `routes/mail.py` 의 `_SYSTEM_FOLDERS`,
  `mail_app/src/lib/folders.js` 의 `SYS_EXACT`.
- **내게쓴메일함은 받은편지함 바로 앞에 고정**한다(둘은 같은 INBOX 를 가른 것이다).
- **이름이 겹치는 메일함은 실제 이름을 덧붙여 보여준다.** `Archive` 와 `Archived` 가
  같이 있어 사이드바에 '보관함' 이 두 줄 서 있었다(2026-09-15, 넷 다 0통이라 `Archived` 정리).
  `\Archive` 특수용도 플래그를 가진 쪽이 진짜다 — 지우기 전에 플래그와 통수를 본다.
- **순서·그룹은 `light_sync.mail_folder_prefs` 에 있다**(계정별). IMAP LIST 에는 순서가 없다.
  설정 > 메일함 관리에서 ⠿ 를 끌어 차례를 바꾸고, 묶음 이름을 적으면 사이드바가 그 이름으로
  묶어 보여준다. 저장은 **목록 통째로** 보낸다 — 한 줄씩 보내면 중간에 끊겼을 때 순서가 엉킨다.

## 1-12. 스팸 — 수신차단 / 수신허용

- 메일서버(mailcow)의 스팸 필터와 **별개**인 우리 목록이다(`light_sync.mail_blocklist`).
- 판정은 `mail_classifier.spam_verdict()` 한 곳에서 한다 — 화면·즉시처리·안전망이 같은 잣대를 쓴다.
- **허용이 차단을 이긴다.** 도메인을 통째로 막고 그 안의 거래처 한 곳만 받는 것이 제일 흔한 쓰임인데,
  차단이 이기면 그게 불가능하다.
- 값은 주소(`kim@x.co.kr`)도 도메인(`@x.co.kr`)도 받고 **한 모양으로 다듬어**(`normalize_block_value`)
  저장한다. 안 맞추면 같은 도메인이 두 줄로 쌓이고 한 줄만 먹는다.
- 보낸사람 메뉴의 [이 주소 수신차단]은 목록에 넣고 **그 자리에서 그 주소 메일만** 스팸함으로
  옮긴다(`/spam/apply` 의 `only`). 목록 전체(500통)를 훑으면 기다리는 동안
  "차단했는데 그대로 있다" 로 보인다.

## 1-13. 자동처리는 **즉시** 돈다 (IMAP IDLE)

```
light_sync_mailwatch.service   ← 새 메일 신호가 오면 그 즉시 (modules/services/mail_watcher.py)
crontab */5                    ← 안전망. 감시자가 죽거나 신호를 놓쳤을 때
        둘 다 modules/scheduler.run_mail_automation() 한 곳을 지난다
```

순서가 뜻이 있다: **① 수신차단 → ② 자동회신·자동전달 → ③ 자동분류.**
차단이 먼저여야 막아 둔 주소에 자동회신이 안 나가고, 분류가 마지막이어야 ②가 메일을 잃지 않는다
(분류가 먼저 돌면 메일을 다른 폴더로 옮겨 버린다).

### 여기서 드러난 것들 (2026-09-15)

- **자동회신·자동전달은 그동안 한 번도 돈 적이 없다.** `.env` 가 `FLASK_DEBUG=true` 라
  `init_scheduler()` 가 호출되지 않고(예약발송이 같은 이유로 crontab 으로 옮겨진 적 있다),
  crontab 에도 없었다. 설정 화면은 있는데 아무 일도 안 일어나는 상태였다.
- **자동분류는 [지금 적용]을 눌러야만 돌았다.** 새 메일에는 안 걸렸다.
- **제목·보낸사람 이름을 안 풀고 비교했다.** IMAP 이 주는 값은 `=?utf-8?b?…?=` 라,
  "제목에 '공고' 포함" 같은 한글 조건이 한 번도 맞은 적이 없다.
  `_decode_header_value()` 를 양쪽(`rules/apply`·감시자)에 넣었다.
- 화면은 `/mail/api/automation-status` 로 **마지막 실행 시각**을 읽어, 안 돌고 있으면
  설정 창에 그대로 적는다. 저장만 되고 아무 일도 안 일어나는 상태를 숨기지 않는다.

### 감시자에서 지킬 것

- IDLE 은 4분마다 되건다(RFC 29분 제한 + 중간 장비가 조용한 연결을 끊는다).
- `idle_done()` 을 빠뜨리면 연결이 IDLE 에 갇혀 다음 명령이 안 먹는다 — `finally` 로 건다.
- 신호가 몰아쳐도 3초로 묶어 **한 번만** 돌린다.
- **자동처리 설정이 있는 계정만** 붙는다. 전 직원 계정에 상시 IMAP 연결을 걸어 둘 수는 없다.
- 사내 서버는 IP 로 붙어 인증서 이름이 안 맞는다 — `MailClient` 와 같이 검증을 끈다.
  여기만 엄격하면 사내 계정은 감시가 아예 안 붙는다(실제로 그렇게 실패했다).

## 1-15. 읽기창의 나머지 기능 (읽음표시 · 인쇄 · 원문보기)

| 무엇 | 어떻게 |
|---|---|
| 읽음 / 안읽음 | **한 자리에서 토글**한다(지금 상태의 반대를 내놓는다). 버튼 둘을 나란히 두면 지금 어느 상태인지는 여전히 안 보인다. **안읽음으로 돌리면 읽기창을 닫는다** — 열어 둔 채 두면 다음에 열 때 서버가 또 `\Seen` 을 달아(`fetch_message`) 방금 한 일이 사라진다 |
| 인쇄 | 서버가 그려 주는 `mail_print.html`(onload 에서 스스로 인쇄)을 **Bearer 로 받아** 새 창에 넣는다. 주소만 새 창에 띄우면 그 창에 세션 쿠키가 없을 때 **로그인 화면이 대신 인쇄된다** |
| 원문보기 | `/mail/api/messages/<uid>/raw`. 헤더까지 그대로 — "진짜 그 사람이 보낸 게 맞나", "왜 스팸함으로 갔나" 는 본문이 아니라 Received·SPF·Return-Path 에 적혀 있다. `?download=1` 이면 `.eml` 로 내려받아 다른 메일 프로그램에서 그대로 열린다 |

- **원문을 봐도 읽음 상태는 안 바뀐다** — `fetch_raw()` 는 `readonly=True` + `BODY.PEEK[]` 를 쓴다.
  안읽음으로 표시해 둔 메일을 원문만 확인했다고 읽음으로 바꾸면 안 된다.

## 1-16. 화면 안내 (가이드 투어)

예전 ERP 메일(`/mail`)과 생김새가 많이 달라졌다. **기능이 없어진 게 아니라 자리를 옮긴 것**인데,
그 말을 안 해 주면 "되던 게 안 된다" 가 된다. 그래서 첫 방문 때 한 번 짚어 준다.

- `lib/tour.js` 에 걸음(제목·설명·가리킬 자리)이 있고, `TourGuide.jsx` 가 그린다.
- 가리킬 자리는 **`data-tour` 표식**으로 잡는다. CSS 클래스를 쓰면 화면을 손볼 때마다 안내가 조용히 깨진다.
- **그 자리가 지금 화면에 없으면 그 걸음은 건너뛴다**(읽기창 버튼은 메일을 열어야 보인다).
  허공을 가리키는 안내가 제일 못 미덥다.
- 구멍은 **아주 큰 그림자**(`box-shadow: 0 0 0 9999px`)로 만든다 — 화면을 실제로 오려낼
  방법은 없다. 밝은 테마는 같은 알파도 옅어 보여 덮개 색을 따로 둔다(`--tour-dim`).
- 한 번 본 사람에게는 다시 안 뜬다(`webmail_tour_v1`). **판을 크게 바꾸면 그 숫자를 올린다.**
- 다시 보기: 툴바의 `?` 버튼, 또는 톱니바퀴 > 단축키·도움말 > [화면 안내 다시 보기].
- 설명에는 **옛 화면에서 어디 있던 것인지**를 같이 적는다(주소록 탭 → 왼쪽 주소록,
  ERP 설정 화면 → 톱니바퀴).
- 걸음 13개. 두 번째가 **메일주소(계정) 바꾸기**다 — 공용계정·외부계정을 함께 쓰는
  사람이 많은데, 왼쪽 위 주소를 누르면 바뀐다는 걸 모르면 남의 메일함을 보고 있다고 여긴다.
- 말투는 **사람이 옆에서 알려주듯** 쓰고, 빈 줄로 문단을 나눈다(`white-space: pre-line`).
  설명이 길어지면 상자 안에서 글만 스크롤되고 상자는 화면을 넘지 않는다.

| 무엇 | 어디 | 알아둘 것 |
|---|---|---|
| **임시보관함 이어쓰기** | 읽기창 [이어서 쓰기] | 없었다. 「나가면 자동 임시저장」까지 만들어 놓고 **이어 쓸 길이 없었다** |

| 휴지통·스팸함 비우기 | 툴바 [비우기] | 서버가 **화이트리스트**로 그 둘만 허용. 받은편지함은 400 |

### 라벨 — 키워드는 이름이 아니라 **id** 다

라벨을 메일에 다는 것은 IMAP 키워드다. 예전 코드는 `label_<이름>` 을 썼는데,
**dovecot 이 한글 키워드를 잘라먹는다**(2026-09-16 실측: `label_업무` → 저장된 플래그 `label_`).
한글 라벨이 전부 `label_` 하나로 뭉개져, 자동분류의 「라벨 달기」도 같은 병을 앓고 있었다.
`mail_classifier.label_keyword(label_id)` 한 곳에서 `label_<id>` 를 만들고,
화면은 **서버가 준 `keyword` 값만** 쓴다(이름으로 만들지 않는다).
덤으로 이름을 바꿔도 이미 달린 라벨이 안 끊어진다.

곁들여 고친 것:
- `/mail/api/folders` 의 labels 가 **5분 캐시**를 타는데 라벨 저장·삭제가 캐시를 안 비웠다 —
  만들어도 사이드바에 한참 안 뜨고 지운 것이 남아 있었다.
- 라벨 저장·삭제에 **계정 권한 확인이 없었다.** 수정·삭제는 넘어온 account_id 가 아니라
  **그 라벨이 달린 계정**을 본다.

### 그 밖에 이번에 드러난 것

- **교체 저장이 첨부를 조용히 날렸다.** `save_draft` 는 `replace_uid` 를 지우고 새로 APPEND 한다.
  이어쓰기가 들고 있던 원본 part 번호는 그 지워진 uid 를 가리켜, **두 번째 저장부터**
  첨부만 빠진 임시본이 남는다(자동저장이 5초마다 도니 반드시 밟는다).
  저장 뒤 새 임시본을 한 번 읽어 part 번호를 다시 겨눈다(`_repointForward`).
- **서명 캐시가 계정 구분이 없었다** — 공용계정으로 바꿔 써도 개인 서명이 붙었다.
  계정별 Map 으로 가르고, 설정에서 서명을 저장하면 그 계정 것만 버린다(`clearSignatureCache`).
- **`styles.read.css`·`styles.settings.css` 는 `styles.css` 맨 앞에서 `@import` 된다.**
  그래서 같은 굵기의 선택자로 맞서면 **나중에 오는 styles.css 가 이긴다.**
  덮어쓰려면 선택자를 한 칸 더 붙여야 한다.
- 두 API 의 시각 모양이 다르다: `receipts` 는 **ISO**, `shared-read` 는 `'%m/%d %H:%M'` 로 이미 포맷돼 온다.

## 1-18. 첨부 미리보기 — **여는 일은 브라우저가 한다**

읽기창 첨부의 [보기].

| 형식 | 어떻게 | 어디 |
|---|---|---|
| 이미지 · PDF | 원본 그대로(blob) | 브라우저 |
| **엑셀** xlsx·xls·csv | SheetJS 로 읽어 표로 | 브라우저 |
| **워드** docx | docx-preview 로 그대로 | 브라우저 |
| **압축** zip | **풀지 않고 목록만** | 브라우저 |
| **한글** hwp·hwpx | 서버가 HTML 로 세워 준다 | `tools/hwp/render.mjs` (rhwp) |
| ppt · doc · 옛 xls | 미리보기 없음 — 내려받기 | |

### 왜 서버에서 브라우저로 옮겼나 (2026-09-17)

전에는 오피스 문서를 회사 문서서버(ONLYOFFICE)로 보내 열었다. 두 가지가 걸렸다.

1. **웹메일 서버가 하는 일은 IMAP 중계와 첨부 내주기가 전부다.** 거기에 문서 변환을
   얹으면 그게 그 서버에서 제일 무거운 일이 된다(한 건에 CPU 몇 초). 김정수 지시:
   *"웹메일 돌리는 서버가 뭐 얼마나 리소스가 클 거라고 덕지덕지 갖다 붙이냐"*
2. **남에게 파는 제품에 못 얹는다** — ONLYOFFICE 커뮤니티판은 AGPL 이다.

오피스 문서는 **ZIP 안의 XML** 이라 JS 로 읽힌다. 그래서 화면에서 직접 그린다.
(한글이 따로인 이유가 이것이다 — hwp 는 바이너리라 파서가 필요하다)

| 라이브러리 | 라이선스 | 크기(gzip) |
|---|---|---|
| xlsx (SheetJS) | Apache-2.0 | 141KB |
| docx-preview | Apache-2.0 | 21KB |
| jszip | MIT | 28KB |

**열 때 비로소 내려받는다(dynamic import).** 메일함만 쓰는 사람 화면은 3KB 만 늘었다.

**pptx 는 일부러 뺐다.** 쓸 만한 것이 `pptx-preview` 하나인데 npm 에는 ISC 라 적혀
있으면서 README 에는 "소스를 공개·수정 배포 불가" 라고 써 있다. 파는 제품에 넣기엔
위험하다. 어설프게 깨뜨려 보여주느니 내려받기로 보낸다.

### 남이 보낸 파일은 **늘 iframe 안에서** 그린다

`sandbox="allow-same-origin"` 만 준다 — `allow-scripts` 를 안 주므로 문서 안에 뭐가
들었든 돌지 않는다. 그림(blob:)이 보이려면 같은 출처여야 해서 그것만 허용한다.
엑셀은 HTML 문자열을 만들어 넣으므로 **이름·값을 반드시 이스케이프**한다.

### zip 목록 — 한글 이름이 깨지는 함정

윈도우 탐색기·알집으로 만든 zip 은 이름을 **CP949** 로 적는다(UTF-8 깃발을 안 세운다).
그대로 읽으면 「?쒓?」 가 된다. **UTF-8 로 엄격하게 읽어 보고 실패하면 EUC-KR 로
되읽는다**(JSZip 의 `decodeFileName`).

실측(2026-09-17): UTF-8 zip·CP949 zip 둘 다 이름·크기·날짜 정상.
풀지 않고 목록만 읽으므로 200MB 까지 열어 준다(다른 형식은 25MB).

- 입구는 하나다: `GET /mail/api/attachment/<uid>/<part>/preview`.
  종류를 보고 HTML 또는 PDF 를 돌려주고, 못 바꾸면 **사람이 읽을 사유**를 415 로 준다
  (화면은 그 문구를 그대로 띄운다 — "내려받아 보십시오").

### 한글은 왜 따로인가

**LibreOffice 에는 한글 필터가 아예 없다**(2026-09-16 실측: `libreoffice-calc` 만 설치돼
있고 hwp 필터는 어느 구성 요소에도 없다). 그래서 `@rhwp/core`(김정수 지시, MIT, Rust+WASM)
를 쓴다. 파서가 Node 라 ERP(파이썬)에서 **subprocess 로 부른다**(`modules/services/attach_preview.py`).

- **`getPageText` 가 아니라 `getPageTextLayout` 을 쓴다.** `getPageText` 는 표 안의 글자를
  통째로 버린다(실측: 심사기준표 .hwpx 가 493자로 나오고 「배점」이 아예 없었다).
  공고문·서식은 표가 알맹이다.
- `getPageTextLayout` 은 글자마다 x·y·크기·글꼴을 준다. **표를 복원하지 않고 그 자리에
  그대로 세우면** 원본과 같은 모양이 나온다 — 절대위치 `<span>` 으로 찍는다.
- wasm 은 **바이트를 직접 넘긴다**. README 의 `'/rhwp_bg.wasm'` 경로 방식은 브라우저용이라
  Node 에서는 못 찾는다.
- 앞 30쪽까지만. 그 이상은 미리보기가 아니라 열람이다.

### 지켜야 할 것

- **임시파일을 `/tmp` 에 두지 않는다** — systemd PrivateTmp 때문에 서비스마다 `/tmp` 가
  달라 다른 프로세스가 만든 파일을 못 찾는다(대용량 첨부에서 한 번 겪었다).
  `.upload_tmp/preview/` 를 쓰고 끝나면 지운다.
- **PATH 를 직접 넣는다** — systemd 가 주는 PATH 에는 venv 뿐이라 node·libreoffice 래퍼가
  dirname·sed 를 못 찾는다(`routes/office.py` 와 같은 사정).
- 변환은 바깥 프로그램을 돌리는 일이다. **시간(90초)·크기(20MB) 제한**을 반드시 건다.
- 한글 HTML 은 우리가 글자를 escape 해 만든 것이지만 **남이 보낸 파일에서 나온 내용**이다.
  화면은 `sandbox=""` 를 건 iframe 에 넣는다(스크립트도 바깥 링크도 안 돈다).

## 1-19. 사내 파일서버(NAS)에서 바로 첨부

예전엔 NAS 파일을 붙이려면 **사람이 NAS → PC 로 내려받아 다시 올렸다.** 같은 파일이
사내망을 두 번 건넜다. 서버가 NAS 와 같은 망에 있으므로 한 번만 건너면 된다.

```
메일쓰기 [파일서버에서 첨부] → 폴더 탐색 또는 경로 붙여넣기 → 경로만 들고 있다가
보낼 때 서버가 사내망에서 직접 읽어 붙인다 (25MB 초과는 지금처럼 우리 Storage 링크)
```

- **외부로 여는 포트는 없다.** 서버(192.168.0.110) ↔ NAS(192.168.0.101) 내부 통신뿐이고,
  받는 사람에게 나가는 모양은 예전과 같다. **시놀로지 공유링크는 쓰지 않는다.**
- 접속 정보는 `light_sync.nas_config` 한 줄. 비밀번호는 메일 계정과 같은 방식으로 암호화하고
  **조회 API 에는 password 필드 자체가 없다.**
- 읽기만 한다 — `modules/services/synology.py` 에 업로드·삭제·이름변경을 부르는 코드가 없다.
- **누가 어느 파일을 붙였는지 로그에 남긴다.** 공유폴더가 여럿 열려 있으므로
  "이 파일이 왜 나갔나" 를 나중에 물을 수 있어야 한다.

### 브라우저는 파일 경로를 안 알려준다

"PC 에서 첨부한 파일이 NAS 경로면 서버가 받아오게" 는 **브라우저 안에서 불가능하다.**
`<input type=file>` 은 `C:\fakepath\이름.xlsx` 만 준다(웹 표준, 드래그앤드롭도 같다).
그래서 붙이는 문을 둘로 만들었다:
1. NAS 탐색기에서 고르기
2. 탐색기에서 **Shift+우클릭 → 「경로로 복사」** 한 것을 붙여넣기
   (`\\magnatech\...` · `\\192.168.0.101\...` 둘 다 인식. `Z:\` 같은 매핑 드라이브는
   어느 공유인지 서버가 알 수 없어 거부하고 그 이유를 적어 준다)

### 창은 **윈도우 탐색기 모양**이다

멋이 아니라 **배울 것이 없어야** 해서다. 왼쪽에 공유폴더, 위에 ← → ↑ 와 주소줄,
가운데에 이름·수정한 날짜·유형·크기. 매일 보던 자리에 같은 것이 있으면 설명이 필요 없다.

- 머리글을 누르면 그 칸으로 줄 세운다. **폴더는 늘 먼저**다(탐색기와 같다).
- 「이 폴더에서 찾기」는 지금 폴더 안에서만 이름을 훑는다(서버를 다시 부르지 않는다).
- **좁아지면 유형 → 수정한 날짜 순으로 칸을 접는다.** 파일을 고르는 화면에서
  이름이 잘리면 무엇을 고르는지 알 수 없다 — 이름이 끝까지 남아야 한다.
- 파일 종류 아이콘은 **SVG**(`FileIcons.jsx`). 색은 종류를 가리는 데만 옅게 쓴다 —
  엑셀 초록·PDF 빨강은 사람들이 20년 봐 온 약속이라 회색으로 통일하면 오히려 못 찾는다.
  도면 아이콘은 처음에 접힌 종이로 그렸다가 **메일 아이콘과 똑같이 생겨서**(렌더해 보고
  알았다) 상자로 바꿨다.

### 창 안에서 뒤로·앞으로

탐색기처럼 **← 뒤로 · → 앞으로 · ↑ 위로** 를 창 안에 둔다(`Alt+←/→`, `Backspace`).

**마우스 옆버튼은 막을 수 없다.** 크롬은 그걸 브라우저가 먼저 처리해서
`preventDefault` 가 안 먹는다 — 실제로 눌러 보니 메일 화면째 뒤로 갔다.
그래서 막는 대신 **받아쓴다**:

```
창이 열릴 때   주소는 그대로 둔 채 history 한 칸을 쌓는다
뒤로가기 신호   창 안에서 '한 폴더 뒤로' 로 쓰고, 한 칸을 다시 쌓는다
더 갈 곳 없으면 창을 닫는다 (사람이 기대하는 다음 단계다)
```

**이때 `lib/route.js` 가 같은 신호를 받으면 안 된다** — 그쪽 `applyView()` 는
작성 중인 메일을 닫으려 든다. 파일서버 창은 열릴 때 `suspendRouting()` 으로
라우터를 잠깐 재워 둔다. 닫을 때 쌓아 둔 칸을 `history.back()` 으로 치우는데,
그 신호는 **다음 차례에 오므로** 0ms 로 풀면 늦는다(그러면 작성창이 닫힌다).
넉넉히 지나고 푼다.

폴더 아이콘은 **SVG** 다. 이모지(📁)를 쓰면 글꼴이 없는 환경에서 네모로 깨진다
(`Icons.jsx` 의 규칙 — 실제로 렌더해 보고 깨지는 것을 확인했다).

### 자동저장이 NAS 를 두드리지 않게

임시저장은 5초마다 돈다. 그때마다 NAS 에서 큰 파일을 받아오면 사내망만 두드린다.
그래서 **임시본에는 경로만 헤더(`X-Mgnt-Nas-Files`)로 적어 두고**, 이어 쓸 때 되살린다.
실제로 받아오는 것은 **보낼 때 한 번**이다.

### 좁히는 것은 **목록뿐**이다

`allowed_shares` 는 **첨부 화면 목록에 보일 폴더**를 정한다. 2026-09-17 현재
`마케팅자료 · 매그나텍 · 사진자료 · 현장관리` 넷(계정이 보는 것은 17개라, 안 좁히면
`homes`·`MailPlus`·`백업` 까지 첨부 화면에 뜬다).

**목록에 없는 폴더도 경로를 직접 적으면 붙는다**(김정수 지시 2026-09-17).
화면을 깔끔하게 하려는 것이지 접근을 막는 장치가 아니다 — 그래서 `check_path()` 는
경로 **모양**만 본다(`..`·역슬래시 차단). 실제로 못 보게 하려면 **NAS 계정 권한에서
잘라야 한다.** 이 구분은 코드 주석·설정 화면 문구에도 같이 적어 두었다.
(그래서 "누가 어느 파일을 붙였는지" 로그가 더 중요해진다)

### 실측 (2026-09-17)

```
설정 저장+연결시험     connected: true · 공유폴더 17개
좁힌 뒤 목록          ['마케팅자료','매그나텍','사진자료','현장관리']
목록 밖 폴더 직접 열기  /연구자료 → 7개 (열린다)
목록 밖 파일 경로로 붙이기 \\magnatech\연구자료\…\Casting bracket.stp → 붙는다 (20MB)
경로 장난질            /현장관리/../../etc → "올바른 경로가 아닙니다"
바깥 주소 저장 시도     8.8.8.8 → 400 (저장도 안 됨)
NAS 파일로 발송        200 → 받은편지함에 첨부 확인
```

**저장 전에 주소를 검사한다** — 처음에는 저장한 뒤 연결 시험을 했는데, 주소를 잘못 넣으면
그게 저장돼 버려 다시 제대로 넣을 때까지 파일서버 기능 전체가 멈췄다(실측에서 밟았다).

## 1-20. 파일서버의 큰 파일 — 흘려보내며 보낸다

`\magnatech\연구자료\…\600W Flood Light Master.CATPart` 같은 126MB 짜리를 붙이면
예전에는 **"파일이 너무 큽니다 (1130MB). 200MB 까지 붙일 수 있습니다."** 로 끝났다.
한도를 **30GB** 로 올리되, **서버가 파일을 손에 들지 않도록** 길을 바꿨다.

```
보내기 누름
  └ 25MB 넘는 NAS 파일이 있나?
      아니오 → 예전대로 그 자리에서 붙여 보낸다
      예    → mail_send_jobs 에 일감 한 줄 만들고 job_id 를 **즉시** 돌려준다
              (요청은 1초 만에 끝난다 — 앞단이 끊을 틈이 없다)
              뒷 실(thread)에서:  NAS → (8MB 조각) → Storage(TUS) → 링크 → 발송
              화면은 1초마다 /mail/api/send-job/<id> 를 물어 진행률을 그린다
```

- **메모리에 안 담는다.** `synology.open_stream()` 이 `iter_content(1MB)` 를 주고
  `storage_adapter.upload_stream()` 이 8MB 씩 TUS 로 밀어낸다. 한 번에 손에 드는 것은 조각 하나뿐.
- **진행률은 DB 에 적는다.** gunicorn 워커가 8개라 메모리에 두면 **조회가 다른 워커로 가서
  "그런 일감 없다"** 가 된다. 다만 8MB 마다 쓰면 너무 잦아 **40MB 마다** 묶어 적는다.
- 5분 넘게 진행이 멈춰 있으면 조회가 스스로 `error` 로 답한다 — 워커가 죽으면 화면이 영원히
  "올리는 중" 으로 남기 때문이다.
- **보내기를 누르면 곧장 발송 화면으로 넘어간다**(`ComposeDone`, kind: `sending`→`sent`/`failed`).
  큰 첨부가 없는 **보통 메일도 같은 화면**으로 간다(`sent`) — 작성 화면이 그냥 사라지면
  나갔는지 아닌지 알 길이 없다. 예약도 같은 카드를 쓴다(`scheduled`).
  작성 화면 위에 창을 띄워 붙들어 두지 않는다 — 몇 분짜리 일을 창으로 막으면 아무것도 못 한다.
- **진행 상황을 지켜보는 것은 화면이 아니라 스토어**(`compose._watchSend`)다. 화면에 두면
  사람이 메일함으로 나가는 순간 감시가 끊겨 **실패를 아무도 모른다.**
  떠나 있는 동안 어그러지면 쓰던 그대로 작성 화면을 되살리고 이유를 적는다(`pending`).

### 여기서 밟은 함정 넷 (전부 실측에서 나왔다)

1. **TUS `Upload-Metadata` 는 쌍 사이가 쉼표다.** 공백으로 이으면 Supabase 가
   `400 Invalid upload-metadata` 를 준다. 한 쌍 안만 공백(`키 base64값`).
2. **시놀로지 `getinfo` 는 없는 경로에도 `success: true` 를 준다.** 대신 줄 안에 `code: 408` 만
   들어 있다. 이걸 안 보면 크기 0 으로 통과해서 한참 뒤 내려받기에서 **502 Bad Gateway** 로
   터진다 — 사람에게는 영문 모를 오류로 보인다. `stat()` 에서 `code`/`name` 을 본다.
3. **뒷 실에는 `session` 이 없다.** `Working outside of request context` 로 발송이 통째로 실패했다.
   `_get_mail_client` · `_promote_large_files` · `_attach_nas_files` 에 `user_id`/`role` 을
   인자로 넘긴다(`_session_get()` 은 마지막 안전판일 뿐).
4. **`get_db()` 는 자동 커밋하지 않는다.** 뒷 실에서 커밋을 빠뜨려 **메일은 나가고
   `mail_large_files` 레코드만 없었다** → 받은 사람 눈에는 링크가 죽어 있다.

→ 그래서 보내는 마지막 한 걸음을 **`_deliver_mail()` 하나로 모았다.** 곧바로 보내는 길과
뒤에서 보내는 길이 갈려 있던 탓에 뒤로 간 메일만 **수신확인·평문 본문·주소록 자동수집·커밋**이
통째로 빠져 있었다. **발송 경로를 새로 만들 때는 반드시 이 함수를 탄다.**

### 실측 (2026-09-17, 126MB CATPart 를 NAS 에서 바로)

```
보내기 요청 응답        1.3초 (job_id 즉시 반환)
업로드                 132,335,712 바이트 / 약 6.5초
전체(발송까지)          10.3초
프로세스 RSS 증가       +33MB  ← 파일 크기(126MB)와 무관하다
받은편지함              대용량 첨부표 + 만료 안내 · /mail/dl/<id> 200
mail_large_files       기록됨 · Storage 에 파일 있음 · 수신확인 레코드 생성됨
```

### 한도는 우리가 아니라 **저장소**가 정한다 (지금 4GB)

흘려보내므로 우리 서버의 메모리·디스크는 한도와 무관하다. 막는 것은
**supabase-storage 컨테이너의 `FILE_SIZE_LIMIT`** — 지금 4GB(4294967296)다.
그 위는 TUS 자리 만들기에서 **413** 으로 튕긴다(디스크는 `/supabase` 에 643GB 남아 있다).

그래서 세 곳이 **같은 4GB** 를 본다. 하나라도 갈리면 **다 올린 뒤에** 실패한다:

| 곳 | 값 |
|---|---|
| `routes/mail.py` `LARGE_FILE_MAX` → `/mail/api/upload-config` → 화면이 붙이는 자리에서 거름 | 4GB |
| `synology.MAX_STREAM` (파일서버에서 바로 붙일 때) | 4GB |
| supabase-storage `FILE_SIZE_LIMIT` (진짜 한도) | 4GB |

**올리려면 저장소부터.** 컨테이너 환경변수를 바꾸고 재시작한 다음 위 둘을 맞춘다.
2026-09-17 에 김정수가 "그대로 4GB 로 둔다" 로 정했다.

그 아래 `MAX_DOWNLOAD`(25MB) 는 **통째로 메모리에 올려도 되는 선**이고,
이 둘 사이는 전부 흘려보내는 길로 간다.

### PC 에서 올리는 대용량도 같은 저장소로 간다

다만 **올라가는 때가 다르다**: PC 파일은 붙이는 즉시 브라우저가 Storage 로 직접
올리고(우리 서버를 안 거친다) 진행률은 첨부 목록에 붙는다. 파일서버 파일은
보내기를 누른 뒤 서버가 옮긴다(발송 화면에 진행률).
PC 쪽 토큰은 30분짜리라 **20분마다 새로 받고**, 조각이 끊기면 TUS 에 받은 자리를
물어 세 번까지 이어 붙인다 — 없을 때는 몇 GB 를 올리고 마지막에 만료로 죽었다.

## 2. 대용량 첨부 (25MB 초과)

메일에 싣지 않고 링크로 보낸다.

```
① 파일을 붙이는 즉시 → Storage 의 mail-temp/ 로 업로드 (아직 DB 레코드 없음)
② 발송/예약이 확정되면 → **옮기지 않고** mail_large_files 에 그 경로를 적는다
                         + 본문에 링크표 삽입
③ 취소·첨부 제거·탭 닫기 → mail-temp/ 에서 삭제 (놓친 건 매일 03시 cron)
```

### 같은 파일이면 한 벌만 둔다

같은 파일(294MB)을 네 번 보냈더니 네 벌이 30일씩 자리를 차지하고 있었다.
이제 **내용이 같으면 저장소에는 한 벌만 두고 `storage_path` 를 나눠 쓴다.**
메일마다 자기 링크(`file_id`)는 그대로 따로 갖는다 — 남의 메일이 보이지 않는다.

```
content_key = sha256( 크기 + 앞 1MB + 뒤 1MB )
```

전체를 해시하지 않는 이유: 브라우저가 GB 를 통째로 읽으면 화면이 굳고,
서버도 30GB 를 한 번 더 읽어야 한다. **앞뒤 1MB 와 크기가 모두 같은 서로 다른
문서는 실무에서 나오지 않는다.** 만드는 곳이 두 군데이니 방식이 갈리면 안 된다:

| 어디 | 어떻게 |
|---|---|
| 브라우저 | `mail_app` 의 `contentKey()` — 앞뒤 1MB 를 `crypto.subtle` 로 |
| 서버(파일서버 첨부) | `routes/mail.py` 의 `_content_key_stream()` — 흘려보내며 앞뒤만 쥔다 |

승격(`_promote_large_files`)에서 같은 지문·같은 크기의 살아있는 줄을 찾으면
**방금 올라온 것을 지우고 있던 것을 가리킨다.**

⚠ 그래서 **파일을 지울 때는 그 경로를 아직 쓰는 다른 줄이 있는지 봐야 한다.**
`app.py` 의 만료 청소가 그 검사를 한다 — 없으면 한 메일이 만료됐다고
남의 첨부까지 사라진다.

실측(2026-09-17): 같은 126MB 를 두 번 보냄 → 지문 같음 · 저장소 1벌 ·
두 링크 모두 내려받기 200 · 73번이 만료돼도 74번이 쓰는 동안 파일은 남는다.

### 옮기지 않는다 — move 는 이름 바꾸기가 아니라 **복사**다

예전에는 ②에서 `mail-temp/` → `mail-attachments/` 로 move 를 불렀다. 실측:

| 크기 | move 1회 |
|---|---|
| 126MB | 수 초 |
| **1.3GB** | **49.5초** |

그동안 화면은 「보내는 중」에 멈춰 있었다(실제 발송 한 건이 14.3초 걸렸다).
지금은 올라간 자리를 그대로 적는다 — **같은 발송이 0.89초.**

그래서 **보낸 첨부도 `mail-temp/` 에 산다.** 보낸 것과 버려진 것을 가르는 것은
위치가 아니라 **DB 에 기록이 있느냐**다. `app.py` 의 `cleanup-mail-files` 는
`mail_large_files` 에 적힌 경로를 건너뛴다 — **이 한 줄이 빠지면 하루 뒤
멀쩡한 첨부가 사라진다.**

### 업로드 경로가 셋

| 크기 | 방식 | 우리 서버 경유 |
|---|---|---|
| ~90MB | 서명 URL 단일 PUT (`/mail/api/upload-sign`) | 안 함 |
| 90MB 초과 | TUS 재개 업로드 48MB 조각 (`/mail/api/upload-token`) | 안 함 |
| 위가 막히면 | 조각 업로드 (`upload-chunk` → `upload-finish`) | 경유 |

브라우저가 Supabase 로 직접 쏜다. service 키는 내주지 않고 서버가 **30분짜리 JWT** 를 발급한다
(`SUPABASE_JWT_SECRET`). 그 토큰으로 되는 건 `company-files/mail-temp/` 아래 쓰기뿐이다 —
`storage.objects` 정책 3개를 넣었다(`sql_editer.sql` 참조).

### 함정

- **막히면 어디서 막혔는지부터 가른다.** 서버 로그에 요청 흔적이 **아예 없으면** 앞단이 막은 것이다
  (Cloudflare 100MB, VPS nginx `client_max_body_size`). 흔적이 있으면 우리 코드다.
- VPS nginx 에도 `client_max_body_size 100m` 이 있었다. `work`·`api` 블록만 `0` 으로 풀고
  **`proxy_request_buffering off`** 를 넣었다. 이게 없으면 VPS 가 파일을 다 받은 다음에야
  전달해서 두 배로 느리다.
- TUS 의 `Location` 헤더는 **스토리지 내부 주소(127.0.0.1:8000)** 를 가리킨다. 경로만 떼어 쓴다.
- 진행률은 **XHR 로 받는다.** `fetch` 는 업로드 진행률을 안 준다 — 처음엔 48MB 조각이 끝날 때만
  갱신돼 33%씩 튀었다.
- **조각 임시폴더에 `/tmp` 를 쓰지 않는다.** systemd PrivateTmp 때문에 서비스마다 `/tmp` 가
  따로 보여 조각을 못 찾는다. `/web/light_sync/.upload_tmp/` 를 쓴다.

### 오래 걸린 버그 하나 — 같은 실수 반복 금지

`api_send()` **함수 안에** `import json` 이 있었다. 파이썬은 함수 안 어디든 import 가 있으면
**그 함수 전체에서 지역변수로 취급**한다 → 함수 앞부분의 `json.loads()` 가 `UnboundLocalError`.
거기에 `try/except Exception` 을 씌워둬서 **오류가 조용히 삼켜지고, 첨부 링크만 사라진 채
메일이 정상 발송됐다.**

→ **부가 데이터를 파싱하는 except 는 반드시 로그를 남긴다.** 조용히 넘기면 기능이 통째로 없어진다.

## 3. 주기작업은 crontab 뿐

`app.py` 끝의

```python
if not app.debug or os.environ.get('WERKZEUG_RUN_MAIN') == 'true':
    init_scheduler(app)
```

가 **실행되지 않는다.** `.env` 에 `FLASK_ENV=development` · `FLASK_DEBUG=true` 가 있어
`app.debug` 가 True 이기 때문이다.

로그의 마지막 `[scheduler] 백그라운드 스케줄러 시작` 이 **2026-03-31** 이었다.
**예약발송이 그때부터 한 번도 실행되지 않았다.** 기능이 안 되니 아무도 안 써서 아무도 몰랐다.

**켜서도 안 된다.** gunicorn 이 `-w 8` 이라 워커 8개가 각자 타이머를 돌려 같은 메일이 8번 나간다.

- 주기작업은 `@app.cli.command()` 로 만들고 crontab 에 건다 (이미 15개가 그렇게 돈다)
- **`cd /web/light_sync &&` 를 빠뜨리면** flask 가 app.py 를 못 찾아
  `Error: No such command` 로 조용히 실패한다
- `modules/scheduler.py` 에 자동회신·자동전달(5분) job 이 아직 남아 있다 — **이것도 안 돌고 있다**
- 정리 작업은 `cleanup-mail-files`(매일 03:00) 하나로 모았다: 만료 첨부 + 하루 지난
  `mail-temp/` + `.upload_tmp/` 찌꺼기

## 4. 네트워크 경로 (속도 문제는 여기부터 본다)

2026-09-15 실측. **코드에서 찾지 말 것 — 경로가 원인이었다.**

Cloudflare **무료 플랜**이 `mgnt.kr` 을 **미국 서부(SJC/LAX)** 에서 처리하고 있었다.
한국(ICN) 회선비 때문에 무료 존은 서울 엣지를 안 준다. 매 요청이 태평양을 왕복했다.

| | 전 | 후 |
|---|---|---|
| 요청 1건 평균 | 0.690초 | **0.107초** |
| 연결 지연 | 135ms | **22ms** |

→ `work.mgnt.kr` · `api.mgnt.kr` 을 **DNS only** 로 뺐다.
공개 홈페이지 `magnatech.co.kr` 은 Cloudflare 유지 — **공격이 오는 곳과 속도가 필요한 곳이 다르다.**

### 구간별 속도

| 구간 | 실측 |
|---|---|
| webserver ↔ Supabase (같은 장비) | 943 Mbps |
| 사무실 회선 | 403↑ / 435↓ Mbps |
| VPS 회선 | 633↑ / 1630↓ Mbps |
| **VPS ↔ webserver (tailnet)** | **147 Mbps ← 병목** |

tailscale 은 사용자 공간 암호화라 회선의 1/3 밖에 못 낸다. **MTU 1420 은 효과 없었다**(되돌림).

그래서 사내 사용자는 tailnet 을 건너뛴다 — `lan.mgnt.kr` 을 **공개 DNS 에 사설 IP(192.168.0.110)로**
등록했다. 밖에서는 연결이 안 되므로 서버가 **접속 IP 를 보고 사내에게만** 내준다
(`routes/mail.py` 의 `_is_lan_client()`).

**48MB 업로드: 5.5 → 14 → 106 MB/s**

### 알아둘 것

- 사무실 공유기는 **80/443 다 닫혀 있다**(VPS 가 공인 IP + tailnet). 포트를 열 필요 없다.
- VPS 접속: `ssh -i ~/.ssh/id_mgnt root@100.101.44.75`.
  nginx 설정은 **`/etc/nginx/nginx.conf` 한 파일**에 다 있다(sites-enabled 는 비어 있음).
  443 은 `ssl_preread` 로 SNI 를 보고 내부 4443 으로 넘기는 스트림 프록시다.
- 인증서는 VPS 가 발급·갱신한다(`*.mgnt.kr`). webserver 는 `/usr/local/bin/sync-mgnt-cert.sh`
  가 매일 04:40 에 받아온다 — 받은 게 진짜 인증서인지 확인한 뒤에만 교체한다.
- **서버에서 속도를 재면 회선을 두 번 쓴다**(나갔다 되돌아옴). 실제 사용자보다 느리게 나온다.
  구간별로 나눠 재야 병목이 보인다.
